# Redis 学生查询缓存接入记录

更新日期：2026-10-15。开发及验证已完成，等待用户审核 PR；生产尚未更新。

## 目标与实际行为

将已有 Redis 服务接入学生前端调用的查询接口，减少重复业务读取和排名构建。浏览器继续通过后端 API 查询，个人明细、时长汇总、核验码及同学院同年级排名由 Redis 缓存，默认有效期 300 秒。

个人缓存同时区分公示批次、审核数据修订号、学号、姓名和学院限制；排名缓存区分公示批次、本人身份、学年、学院、年级、页码及每页数量。身份和查询范围经过 SHA-256 后放入缓存键，排名在脱敏后才缓存，另一名学生不会得到前一名学生的完整身份。

后端在有请求时最多每秒检查一次公示指针及审核修订号。同一进程发布后立即切换公示版本；其他进程发布或审核数据变化会在下一次版本检查后使用新键。旧键最多保留五分钟后自然到期，正式时长仍只取冻结的公示快照。修改审核库只更新查询中的审核进度，不提前改变正式时长或排名。

同一进程中，同一键的并发缓存未命中会共用一次业务读取。Redis 不可用时回到既有查询路径：完整握手最多等待 1 秒，命令最多等待 500 毫秒；失败后暂停连接尝试 5 秒，然后在下一次请求时重试。损坏 JSON、未配置或无效连接配置不会阻断正常查询，失败的业务读取不会写入缓存。

导入后的旧缓存清理兼容当前 Redis 客户端的字符串扫描游标。可编辑的后台审核库查询继续直接读取 PostgreSQL。查询计数仍写入 PostgreSQL，因此缓存命中减少的是业务记录读取，查询计数不会因命中缓存而丢失。

排名范围使用与个人查询相同的统一学生资料，避免某条历史记录缺少年级时错误拒绝排名。HTTP 响应保留 `Cache-Control: no-store`，浏览器及代理不缓存个人结果。

## 服务配置

Compose 中 Redis 保留既有 AOF 和数据卷，新增 `--maxmemory 128mb --maxmemory-policy allkeys-lru`，达到容量上限时淘汰缓存。当前生产 Redis 的运行配置尚未改变；这些参数需在 PR 审核、合并并发布时应用。

本次没有增加依赖，没有数据库迁移，也不涉及 Supabase 镜像结构或业务记录变更。
