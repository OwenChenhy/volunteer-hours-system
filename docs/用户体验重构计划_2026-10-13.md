# 用户体验重构计划

日期：2026-10-13。状态：开发与隔离验证已完成，PR待用户审核。实际交付与验证见 `用户体验重构开发记录_2026-10-13.md`。

## 目标与范围

本轮围绕三个体验问题推进：低权限用户只看见可使用的功能；补齐用户账号、活动和时长记录的删除操作；将活动创建、名单录入、导入、审核进度连成清晰流程。

用户已确认“无法删除”同时包含用户账号以及活动/时长记录。下文的删除权限和处理方式为建议默认规则，实现时按此作为评审基线。

本计划依据当前本地工作区源码和项目进度文档。工作区存在较多既有未提交改动；本轮检查没有进行线上浏览器试用，也没有重新核对远端版本。已有上线和验证信息以原进度文档记载为背景。

## 当前问题与依据

| 现状 | 对体验的影响 | 主要位置 |
| --- | --- | --- |
| 13个后台模块直接渲染，未读取当前用户权限；概览的快捷入口和数据请求也固定执行 | 无权限入口可见；仅隐藏侧栏仍可能在首页报错 | `frontend-admin/src/App.jsx` 的模块配置、App、OverviewPage |
| 后端已有角色能力表，前端尚未使用；登录返回用户，`/auth/me` 当前仅返回Token中的身份 | 前后端无法统一决定入口和操作；权限变更不能可靠刷新 | `backend/src/middlewares/rbac.js`、`backend/src/routes/auth.js` |
| 账号仅支持创建、启停、重置密码；认证仅校验JWT | 缺少删除入口；禁用或删除后，旧会话需要额外处理 | `backend/src/routes/users.js`、`backend/src/middlewares/auth.js` |
| 活动只有编辑、归档、恢复；创建与名单填报分属不同页面 | 用户不清楚创建后的下一步；归档与删除容易混淆 | `frontend-admin/src/App.jsx` 的ActivitiesPage、SubmitPage |
| 导入具备预览、错误分类、事务和防重，但高级参数、问题确认、累计表替换混在一屏 | 操作顺序不明确，成功数量和跳过数量难判断 | App中的ImportPage、`backend/src/routes/import.js`、`backend/src/services/importService.js` |
| 累计表替换依赖备注完全匹配，导入记录直接进入approved | 普通备注承担数据集身份；活动名单上传不能直接复用该入库路径 | `backend/src/services/importService.js` |

## 阶段一：权限决定入口（P0）

1. 以现有后端能力表作为权限来源，让当前用户接口返回最新身份、能力和数据范围。前端用同一套判断控制侧栏、首页卡片、快捷入口和操作按钮。
2. 登录后按角色进入可使用的工作台；身份加载期间不展示完整菜单。页面切换统一校验权限，越权直达或权限变更后回到可使用页面。
3. 首页按权限请求数据，避免组织者仍请求管理员统计或审核接口。保留后端接口授权与学院、活动归属校验。
4. 账号启停、删除、角色或学院变更后，旧访问Token和刷新Token按最新账号状态处理；前端同步更新菜单和当前页面。

首版导航按现有职责收敛，不扩张现有数据范围：

| 角色 | 建议主要入口 |
| --- | --- |
| 活动组织者 | 我的活动、名单填报、我的提交进度 |
| 学院管理员 | 学院工作台、本人负责的活动、学院名单提交与进度、学院学生查询/汇总 |
| 数据管理员 | 审核、累计库导入、问题复核、学生查询、统计，以及当前获准的运维/日志入口 |
| 只读审计员 | 获准的查询、汇总、复核查看、运维和日志；隐藏写操作 |
| 管理员、超级管理员 | 上述管理功能、用户管理、统一发布 |

当前admin与super_admin均为全权限；本轮先沿用这一事实。学院活动是否允许同学院协同管理需要另行确定，首版沿用现有“本人创建活动”的范围。

**验收：** 六种角色分别登录，所有可见页面均能正常加载；无权限入口与按钮不显示，越权接口仍拒绝。账号状态或权限变化后旧会话不继续沿用旧权限。

## 阶段二：补齐删除与操作规则（P1）

| 对象 | 建议首版行为 | 约束和用户反馈 |
| --- | --- | --- |
| 用户账号 | 管理员可删除，采用逻辑删除，立即停止登录及已有会话 | 保留活动创建、审核和操作历史的关联；禁止删除自己和最后一个可管理账号 |
| 尚无名单记录的活动 | 有管理权限的创建者或管理员可删除，支持恢复 | 删除前展示活动名称；列表默认隐藏已删除项 |
| 已有关联记录的活动 | 先展示记录数、审核状态及发布影响，再进行权限允许的撤回/作废或归档 | 活动删除不隐式级联删除时长；归档只表示停止继续填报 |
| 未审核时长记录 | 提交者可撤回自身范围内记录，修正后重新提交 | 学院管理员仍受所属学院限制；操作保留痕迹 |
| 已审核时长记录 | 具备审核管理权限的人员可作废，填写原因并预览影响 | 保留原记录和审计；已发布结果通过下一次统一发布更新 |

账号表、活动、时长和审计存在关联，首版采用可追溯的删除/作废方式。实现需统一有效记录口径，覆盖列表、审核待办、汇总、排名、防重和发布计算；恢复时重新校验重复与状态冲突。

按钮统一放在列表“更多操作”和详情页。确认框说明具体对象、影响条数和后续动作；执行中防止重复点击，完成后更新列表并提供结果反馈。

**验收：** 删除与恢复后关联信息可查；越权删除、跨学院操作、自删和最后管理账号删除被拒绝；作废不会误改当前公示快照，下一次发布的汇总和排名正确。

## 阶段三：串联活动与名单流程（P1）

活动列表作为主要入口，顶部提供“新建活动”，创建表单进入独立流程页。详情页集中展示基本信息、名单、审核进度和允许的操作。

```mermaid
flowchart LR
  A[填写活动信息] --> B[录入参与名单]
  B --> C[校验与预览]
  C --> D[确认提交审核]
  D --> E[等待审核]
  E --> F[通过待发布]
  F --> G[统一发布后生效]
```

- 基本信息：名称、真实起止时间和负责单位优先；地点、描述等次要内容分组。默认带出账号所属单位，展示自动计算的学年/阶段，需要覆盖时再展开。
- 名单录入：提供表格编辑、Excel复制粘贴、模板上传三种入口，最终进入同一校验预览；始终显示当前活动，避免重新选错活动。
- 预览：显示人数、总时长、重复与错误，允许返回修正；错误定位到行和字段。修改输入后旧预览失效。
- 提交结果：明确显示“已提交，等待审核”和查看入口；活动详情展示待审核、被驳回、通过待发布、已发布的记录进度。
- 第一步保存后可稍后补名单；离开有未保存输入时提醒，返回上一步保留输入。首版优先做好流程内状态保留，跨会话名单草稿作为后续增强。

活动可包含审核状态不同的记录，详情展示数量分布，避免把整场活动误标为全部通过。

**验收：** 学院管理员从新建活动到提交名单连续完成一次操作，无需另找填报入口；驳回原因可见，修改再提交路径明确。活动明细使用真实日期，现有历史活动继续保留“2026年10月之前导入的活动”的未知日期标记。

## 阶段四：导入向导与结果页（P1）

先区分两类目的，界面沿用一致的步骤：

| 目的 | 使用者与入库规则 |
| --- | --- |
| 为当前活动上传参与名单 | 组织者、学院管理员在本人活动范围内操作，走名单提交权限，记录进入待审核并关联活动 |
| 办公室导入/更新累计时长库 | 具备`import:manage`的人员操作，沿用既定管理员导入与统一发布规则 |

```mermaid
flowchart LR
  A[选择目的与目标] --> B[上传文件]
  B --> C[解析并处理问题]
  C --> D[核对变更摘要]
  D --> E[执行并查看结果]
```

1. **选择目标：** 活动名单自动绑定当前活动；累计库明确数据集、统计范围和是否更新已有版本。首次导入与更新旧库使用清晰文案，备注回归说明用途，逐步改为稳定的数据集标识，兼容既有批次。
2. **上传解析：** 提供对应模板与样例；先自动匹配已支持表头，对未识别列给出明确提示。高级学年/阶段/年级默认值按需展开。
3. **处理问题：** 按正常、重复、待确认、错误筛选。重复默认跳过并解释原因；问题行支持修正、按明确理由确认或显式跳过，避免一次“确认全部”掩盖问题。可下载错误清单回原表修正。
4. **核对影响：** 展示预计新增、替换、跳过、待审核数量及人数/时长变化。累计库更新展示旧范围和新范围的差异，确认动作直接说明“更新哪一个库”。
5. **结果页：** 持续保留批次编号、实际处理数量、错误清单和后续入口。区分“提交待审”与“导入完成待发布”。提交超时先核对结果再重试，防止重复记入。

复用已有解析、事务、防重和并发保护能力。预览与确认必须使用同一批标准化数据，绑定用户、目标及数据版本；文件、默认值、跳过选择或目标变化后重新校验。确认阶段仍由服务端检查权限、日期、学院、重复和覆盖范围。

**验收：** 首次上传、同文件重传、同范围累计更新、跨年级文件、异常行跳过、0时长/调整行、预览过期及请求中断均有明确结果；普通名单上传不会成为绕过审核的全库导入入口。

## 实施顺序与交付物

| 里程碑 | 内容 | 交付与完成标准 |
| --- | --- | --- |
| M1 | 权限入口、角色工作台、账号管理与删除 | 角色/页面/动作矩阵；菜单及会话规则实现；六角色权限验收 |
| M2 | 活动详情、创建向导、名单流程及撤回/作废 | 活动完整交互原型；一次新建到待审演示；删除和时长口径验证 |
| M3 | 两类导入向导、累计库更新、结果反馈 | 导入原型与契约；真实格式的脱敏表格验收；防重及替换对账 |
| M4 | 完整业务试用与发布检查 | 桌面/手机浏览器验收，服务器测试与构建，发布前后数据对账和进度文档更新 |

按M1→M2→M3→M4推进，权限与记录生命周期先定，再接入新的页面和导入步骤。实现前先给出活动与导入流程原型，确认页面关系和主要按钮。

实施范围优先复用现有React/Vite、能力表、表格解析和审计；将App中的相关页面按流程拆出，提取最少量的权限判断、确认框和步骤指示组件。先完成上述可验收流程，再评估全站视觉统一和持久草稿增强。

测试、构建和最终验证按项目已有约定在服务器开发环境执行。阶段一至四的开发与隔离验证已完成；生产迁移与发布需在用户审核PR后另行授权。

## 完整验收例子（预期行为）

学院管理员登录只看见自己的工作入口 → 新建带真实时间的“校园志愿活动” → 从活动页面上传名单 → 修正无效时长并核对重复项 → 提交后显示待审核 → 办公室驳回一条并说明原因 → 学院修正再提交 → 全部通过后显示待发布 → 管理员统一发布 → 学生查询正式时长与排名更新。

若发现误建空活动，创建者可以删除；若已提交名单，按权限撤回或由审核人员作废，详情明确展示对下一次发布的影响。以上是计划验收场景，尚未实际执行。
