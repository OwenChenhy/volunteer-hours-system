# 月度统一发布与审核进度

2026-10-12上线。每月更新最新累计时长库，保留学年汇总与历史明细。学院提交和办公室审核期间，学生正式时长、明细与排名沿用上一发布版；办公室完成全部审核后，学校管理员统一发布新版。

## 操作流程

1. 学院账号在管理端“活动”创建活动，在“填报”选择活动，提交参与学生的学号、姓名、时长等信息。学院管理员未填写学院时使用账号所属学院；已有学生的年级可从库中取得，新学生的年级应由学院填写、办公室核对。
2. 学生在查询端输入本人学号和姓名，可以看到自己的“活动审核进度”。“审核中”及“审核通过，待统一发布”的活动不计入当前公示累计时长或排名。只有待审活动、尚无已发布记录的学生也可以查进度，此时正式时长为0。
3. 管理员或数据管理员在“审核”处理记录。学院管理员负责提交和查看，不再自行审核通过；学院账号只能提交所属学院、自己负责活动的记录。
4. 学校管理员或超级管理员打开“统一发布”，查看待审核数、已通过记录数、当前公示和发布历史。任何记录仍为待审核时，发布按钮禁用，服务端也拒绝发布。
5. 全部审核完成后，填写公示月份和说明，点击“全部审核完成，统一发布”。系统生成累计快照和汇总，完成后切换公示版。审核驳回的活动不进入累计时长。
6. 学生重新查询即可看到新公示和排名。查询页不再每30秒轮询；再次查询可以取得当时的审核进度。

正式入口：[管理端](https://zysc.hanyao.me/admin/)、[学生查询](https://zysc.hanyao.me/query/)。

## 数据与计算

- 审核库仍为 `volunteer_logs`。通过审核只是进入待发布状态，不直接改变正式公示。
- `publication_batches` 保存不可变的累计发布快照、预计算年度汇总、计算规则、说明、发布人员和时间；`publication_state` 指向当前发布版。
- 在数据库事务内阻止写入交叉、检查剩余待审记录并生成快照。服务器准备好学院/年级范围的排名索引后再切换；延迟读请求不会覆盖刚发布的缓存。
- 正式查询读取已发布记录和预计算排名，个人审核进度按学号姓名查询审核库。后台人员查找、复核和管理端学年汇总继续读取审核库，供办公室核对未发布的变化。
- 同时长按1、1、2的方式并列；排名、合计、分页与原SQL对账。公开表中其他同学的学号姓名仍脱敏，公开明细及进度不包含内部记录UUID、电话或原始来源文件。
- 服务启动会加载当前快照和内存索引。首次部署将已有公示的34,277条、324,663.4小时初始化成“历史公示基线”，业务记录与时长保持原值。之后的数据发布由管理员操作。
- 同月同一数据版本的重复发布复用同一快照；没有数据变化时可以选择新的公示月份。当前发布检查覆盖整个审核库，不按活动日期自动切分待审批次。

## 访问量与验证

采用服务器内的私有正式数据副本测试；2000个不同学生集中查询，共用一个出口，每人经过测试Nginx完成个人查询和汇总表请求。

| 指标 | 结果 |
| --- | --- |
| 用户数 / HTTP请求数 | 2000 / 4000 |
| HTTP结果 | 全部200，无429或5xx |
| 95%完整查询耗时 | 约19.0秒 |
| 最慢完整查询耗时 | 约19.5秒 |
| 整批测试耗时 | 约20.3秒 |
| 真实数据排名范围对账 | 310个范围与原SQL一致 |
| 正式业务记录与时长 | 测试和发布前后保持34,277条、324,663.4小时 |

这是服务器内HTTP结果，包含业务查询、Nginx代理和响应解析，不包含学生所在网络、外层HTTPS及浏览器展示时间。2000人30秒目标在该环境通过；公网完整体验仍需学校网络人工试用，未承诺3000人同秒查询。

查询限流改为“同一出口下每个学号每分钟10次”，并在正文校验之后计数；同一学校出口的不同学号不互相占用个人查询限额。版本、访问及计数接口使用独立出口限额。Nginx改为自动worker、每worker4096连接；后端及Nginx容器打开文件软限制16384。限额校验和可信代理IP行为有回归检查。

其他验证包括待审学生查询、批准但不发布、待审阻止发布、权限边界、驳回、跨发布版本检查、重复发布、并发缓存切换、公开字段脱敏、原有六组回归、两前端构建和后端镜像。浏览器自动化工具初始化时报“系统找不到指定的路径”，本次未完成浏览器点击全流程；工程/API、公网页面和资源检查已完成。

## 镜像与恢复

- Supabase镜像包含发布快照和当前版指针，相关表开启RLS，只供 `service_role` 访问。普通前端不直接读取快照表。
- 首次同步累计快照时触发REST角色继承的8秒数据库超时，主站自动回退。随后将可信镜像上传角色的语句限时设为60秒并重载配置，重新发布与同步成功。[Supabase超时说明](https://supabase.com/docs/guides/database/postgres/timeouts)。
- 主库与镜像当前发布指针一致，快照JSONB摘要均为 `ff3a84d34d146ce775beae787123cf87`。现有 `public_counters` 的RLS无策略INFO提示表示客户端未获准访问，未开放该表。[提示说明](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy)。
- 发布前服务器本地备份：`/opt/volunteer-system-release-backups/20261012T142350Z-before-monthly`；原后端镜像另保留 `volunteer-system-backend:before-monthly-20261012`。
- 私有证据目录：`/opt/volunteer-system-dev-20261008/monthly-checks/`，包括隔离回归、HTTP测试、发布、镜像同步及公网核对记录。测试副本和测试容器已清理，未在正式库添加测试学生或测试活动。
- 现有每日备份和镜像任务继续运行；手动发布后普通查询立即使用主库已发布版，云端镜像随同步任务更新。所有发布快照保留，后台展示最近12条；数据随月度发布积累，应纳入容量复查。
