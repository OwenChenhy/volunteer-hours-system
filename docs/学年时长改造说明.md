# 学年时长首版：使用与发布说明

日期：2026-10-08。首版开发、测试和构建在服务器独立开发目录完成，生产服务尚未发布本次变更。

## 使用

- 管理端“学生查询”支持学号、姓名、可选联合条件，以及同名候选的分页。选择某条活动可修改时长、身份和归属；可将身份修正同步到此人其他记录。
- 修改时长填写更正后的值。0表示该项时长作废；负数表示调整扣减，必须填写原因。修改前后通过既有复核记录保留。
- 管理端“活动”按学年和阶段筛选，创建活动默认按日期归类，亦可明确选寒暑假补录；编辑活动时间/归属会同步到关联时长记录。
- 管理端“学年汇总”每人一行，显示上半年、下半年、寒暑假、待确认累计和净总时长，按净时长降序。相同时长并列，下一名次连续；分页不重新计算名次。
- Excel采用下载的标准模板，可混合年级、多工作表。年级来自行内字段、明确的年级工作表，或已有唯一的身份资料；不根据未知学号规则猜测。
- 普通行填写正时长；调整行在“录入类型”填写“调整”或“扣减”，并填写“调整说明”。重复文件或同一学生/活动/日期的重复普通行会跳过；相同扣减金额与原因的调整会去重。
- “累计服务时长”表必须勾选累计表替换并提供固定批次备注，以替换同一数据集的旧批次。该固定备注必须用于唯一的数据集，不能和其他学院或不同期间混用。
- 历史累计项没有可靠活动期间时，显示“待确认累计”，参与净总时长但不伪造阶段；管理员确认后可以明确指定归属。
- 用户输入本人学号姓名后，可看本人的年度汇总和同学院同年级的汇总排名表。其他人姓名和学号脱敏；学院管理员的汇总与修改保留学院权限范围。
- 查询缓存包含数据库数据版本。页面每30秒检查版本变化，修改保存后的再次查询即读取最新数据。

## 默认规则与配置

当前默认学年9月开始，9—1月为上半年，3—6月为下半年，2、7、8月为寒暑假补录。寒暑假合为一列，允许单条活动或整批导入明确覆盖。业务负责人需确认学校实际规则。

后端配置：`ACADEMIC_YEAR_START_MONTH=9`、`ACADEMIC_UPPER_MONTHS=9,10,11,12,1`、`ACADEMIC_VACATION_MONTHS=2,7,8`。月份互斥校验会拒绝假期与上半年重叠的配置。Docker Compose已暴露这些参数。

`FEEDBACK_EMAIL`需配置办公室真实地址，才启用邮箱入口。当前未提供地址，用户页面显示待配置及联系学院负责人的提示。此版本不含站内反馈工单。

现有0.1小时精度保留。跨年归类基于真实日期或明确学年/阶段，不基于补录当天。自然日期使用ISO日期文本，在线活动开始时间按上海时区转换为日期。

## 发布准备

先确认办公室邮箱、月份口径、名单可见范围和真实Excel样例。生产目录已有恢复工作改动，应按开发副本对基线c72cd86的增量应用，避免覆盖原有改动。

发布时先生成并验证既有数据库备份，再迁移主库`005_academic_hours.sql`。不要把测试库或测试记录带入生产。

现有`scripts/sync-supabase-database.py`使用`SELECT *`镜像完整行。同步前需在Supabase镜像执行`supabase/migrations/202610080001_academic_mirror.sql`，兼容活动、记录和批次新增字段及负时长约束，并保留既有RLS。新表`data_versions`只服务于主库查询，不需要加入当前镜像表清单。此步骤尚未执行。

构建发布后端镜像与两个前端时使用服务器；部署后验证原有健康、查询、学院边界、版本刷新和备份/镜像同步。退回旧应用版本时保留新增列和已产生的调整记录，避免破坏数据；不要直接恢复旧的正数约束。
